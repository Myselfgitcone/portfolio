An Iceberg fanout writer OOM on a 10-year backfill, and the one-line fix

9,049 rows blew a 1 GB Spark heap and put the stream in a crash loop. The rows were not the problem. The 2,500 open Parquet files behind them were.

The setup

Grainflow streams CBOT grain futures, NWS weather and USDA crop ratings from Kafka into Apache Iceberg bronze tables with Spark Structured Streaming. One job, one foreachBatch per contract. Every table is partitioned by day: for price bars, partition: { field: bar_start, transform: day } in the contract YAML, which generates the Iceberg DDL.

The whole stack runs on a laptop under docker compose. Spark is local[2] with the default 1 GB driver. In local mode the executors live inside the driver JVM, so "driver memory" is all the memory the job has.

Live, this is easy. A 30-second micro-batch holds a few minutes of 1-minute bars, all from today. One partition, one file, done.

The failure

To test the weekly signal over nine growing seasons I backfilled ten years of daily bars through the same Kafka topic the live producer uses: 9,049 rows, one per contract per trading day, about 2,500 distinct days. The stream's maxOffsetsPerTrigger is 50,000, so the entire backfill arrived in a single micro-batch.

The job died with java.lang.OutOfMemoryError: Java heap space. The container restarted, Structured Streaming replayed the same micro-batch from the checkpoint, and it died again. A clean crash loop, every 40 seconds.

9,049 rows is nothing. A few hundred kilobytes. Nothing about the data explained a gigabyte of heap.

What was actually in memory

Iceberg's Spark writer has two strategies for partitioned tables.

  • Clustered writer. Expects each task's rows to arrive grouped by partition. It keeps one open file; when the partition value changes it closes that file and opens the next. If a partition it already closed shows up again, it fails fast.
  • Fanout writer. Makes no assumption about order. It keeps one open file writer per distinct partition the task has seen, and closes them all when the task finishes.

For streaming writes Iceberg turns the fanout writer on by default, and that is the right default: micro-batches are rarely sorted, and a clustered writer meeting unsorted data would throw on every batch. For a live stream touching one or two partitions per batch, fanout costs nothing.

It costs a lot when one micro-batch spans 2,500 days. Two tasks, each seeing most of those days, is on the order of 5,000 open Parquet writers at once. Each one owns column buffers, a dictionary encoder per column, page buffers and the file footer it has not written yet. None of them flush until the task ends. With everything inside one 1 GB JVM, the heap filled before the first file closed.

The lesson in one line: the fanout writer's memory is proportional to distinct partitions per task, not to rows. A backfill changes that number by three orders of magnitude without changing the row count much at all.

The fix

The clustered writer only needs rows ordered by partition within each task. That is sortWithinPartitions, a local sort with no shuffle. Then tell Iceberg it can trust the order.

# spark/jobs/stream_to_bronze.py
+ CLUSTERED_WRITE = {"distribution-mode": "none", "fanout-enabled": "false"}
+
+ def clustered_by_partition(rows: DataFrame, contract: Contract) -> DataFrame:
+     return rows.sortWithinPartitions(contract.partition_field)

  def batch_writer(contract: Contract):
      ...
-             good.writeTo(table).append()
+             clustered_by_partition(good, contract).writeTo(table).options(
+                 **CLUSTERED_WRITE
+             ).append()

Three choices in there, each deliberate.

  • sortWithinPartitions, not orderBy. A global sort would shuffle the batch across tasks. The clustered writer does not need that; it needs order inside a task.
  • fanout-enabled: false. Overrides the streaming default so Iceberg uses the clustered writer. With the sort in place it never sees a closed partition again, so the fail-fast path never fires.
  • distribution-mode: none. hash would shuffle rows so each partition is written by one task, giving fewer files. On two local cores that shuffle is pure overhead, and Dagster already runs nightly compaction on the bronze tables. In a cluster with many executors I would flip this to hash.

The partition field comes from the same contract YAML that generates the table, so the sort column can never drift from the partition spec.

I also raised the driver to 1.5 GB in spark-defaults.conf. That is headroom, not the fix. Before the sort, 1.5 GB died the same way.

Proving it

A unit test feeds the writer bars from five days in scrambled order, collapses them to one task, and asserts the rows come out sorted and the fanout option is off. It runs in CI on every change, on a local Spark with no cluster.

def test_rows_are_clustered_by_partition_before_writing(spark, contracts, price_bar):
    contract = contracts["price_bar"]
    days = ["2019-03-04", "2017-01-03", "2024-06-10", "2017-01-03", "2019-03-04"]
    bars = [{**price_bar, "bar_interval": "1d", "bar_start": f"{d}T05:00:00+00:00"} for d in days]
    good, _ = job.split(job.decode(kafka_rows(spark, bars), contract), contract)

    ordered = job.clustered_by_partition(good.coalesce(1), contract)

    starts = [r.bar_start for r in ordered.collect()]
    assert starts == sorted(starts)
    assert job.CLUSTERED_WRITE["fanout-enabled"] == "false"

Then the real run. The same 10-year backfill landed in one micro-batch in about 38 seconds, memory stayed flat, and batch time fell back to about 2 seconds once the stream caught up. Those 9,049 bars are what the nine-season result on the Grainflow page is computed from.

What I would do differently in production

SituationChoice
Backfill through the streamCap maxOffsetsPerTrigger so one micro-batch cannot span years, or run backfills as a batch job and leave the stream for live data.
Many executorsdistribution-mode: hash so each partition is written by one task and the small-file count drops at write time instead of at compaction.
Unsorted data, must use clusteredDo not. The clustered writer fails fast on a reopened partition, which is a better failure than a slow OOM, but the sort is cheap enough to just always do.
Any streaming Iceberg writeKnow which writer you are on. Fanout is the default and it is correct, right up until the partition count per batch grows.
